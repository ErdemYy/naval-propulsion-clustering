**Project:** Naval Propulsion Clustering  
**Academic Title:** *Unsupervised Discovery of Operating and Performance Degradation Profiles in Naval Gas Turbine Propulsion Systems*  
**Architecture Document Version:** 1.0.0 (Phase 0 Baseline)

---

## 1. System Overview & Architectural Invariants

The Naval Propulsion Clustering system is designed as a modular, reproducible, local Python research and software platform. Its core scientific objective is to explore unsupervised structure in multivariate gas turbine sensor streams without access to ground truth degradation indicators ($kMc$, $kMt$).

### The Core Architectural Invariants:
1. **The Target Separation Invariant:** The feature matrix $\mathbf{X}$ provided to unsupervised models (scalers, feature extractors, clustering algorithms) must never contain $kMc$ or $kMt$. Target coefficients are strictly quarantined inside a dedicated `DatasetContainer.targets` attribute and consumed only during post-hoc statistical validation.
2. **Deterministic Reproducibility:** Every stochastic transformation (clustering initialization, subsampling) must accept an explicit, centralized random seed.
3. **No Cloud Dependencies:** The entire execution loop—from data ingestion through clustering to the Streamlit visualization interface—runs entirely locally on standard Windows workstations.
4. **Decoupled Configuration:** Execution hyperparameters, data paths, and algorithm specifications are declared in YAML configurations rather than hard-coded into implementation logic.

## 5. Research Notebooks vs. Production Code Boundary

A common antipattern in academic machine learning is writing the entire research implementation inside disordered Jupyter notebooks. This project enforces a strict boundary:

1. **Role of `notebooks/`:**
   - Exclusively for *scratchpad exploration*, interactive visual verification, distribution checks, and preliminary prototyping.
   - Notebooks **do not declare monolithic algorithms**; instead, they import functions, dataclasses, and pipelines from `src/naval_propulsion`.
   - Notebooks serve as human-readable narrative records accompanying specific milestone phases.

2. **Role of `src/naval_propulsion`:**
   - Production-grade, fully typed, tested Python code.
   - Houses all reusable transformations, mathematical logic, metric calculations, and data validations.
   - Driven by automated unit and integration tests executed in CI or local test commands (`pytest`).

3. **Role of `experiments/`:**
   - Decoupled experiment runner scripts execute standardized sweeps using configuration files (`experiments/configs/*.yaml`), saving output metrics and serialized models without requiring interactive notebook execution.

## 6. Planned Experiment Lifecycle

```text
1. HYPOTHESIZE  ---> Define research goal and cluster hypothesis in EXPERIMENT_LOG.md.
2. CONFIGURE    ---> Create declarative YAML in experiments/configs/exp_xxx.yaml.
3. EXECUTE      ---> Run experiment via headless CLI entrypoint using fixed seed.
4. VALIDATE     ---> Compute intrinsic metrics (Silhouette, Davies-Bouldin) and
                     conduct post-hoc statistical hypothesis tests on kMc & kMt.
5. PERSIST      ---> Save serialized model, metric JSON, and plots to experiments/outputs/.
6. RECORD       ---> Update EXPERIMENT_LOG.md with metrics and scientific conclusion.
```

## 7. Deferred Architectural Decisions (Awaiting Dataset Inspection)

In accordance with strict engineering discipline, the following decisions are deliberately deferred until the raw dataset is physically ingested and inspected in Phase 1:

1. **Delimitation & Column Naming:**
   - The exact delimiter (whitespace, tab, comma) and presence/absence of header lines in the raw UCI dataset will be verified directly from the source file.
2. **Zero-Variance Feature Handling:**
   - Several sensor features in simulated gas turbine datasets are known to have zero or near-zero variance across operating points. The exact threshold and drop strategy will be decided after variance profiling in EDA.
3. **Scaling Strategy:**
   - Choice between `StandardScaler` (Z-score), `RobustScaler` (quantile-based), or `MinMaxScaler` depends on the presence of skewness and heavy outliers in raw sensor telemetry.
4. **Optimal Cluster Count ($k$):**
   - $k$ will be discovered through empirical evaluation (Elbow, Silhouette, Calinski-Harabasz sweeps), not arbitrarily hardcoded.
5. **Operating-Point Conditioning Strategy:**
   - Determination of whether clusters naturally split along speed/load regimes, and whether residual-based normalization (subtracting operating envelope baseline) is necessary to isolate degradation signatures.
